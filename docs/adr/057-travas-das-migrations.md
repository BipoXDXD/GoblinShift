# ADR 057. Cada migration na sua transação, com `lock_timeout` curto e retry limitado

- **Estado:** aceito (coordenação, 14/11, por delegação do dono)
- **Plano:** [3.8](../GoblinShiftPlan.md#s3-8) (implantação, expand/contract)
- **Relacionado:** issue #442, ADR 056 (substitui o item "Transação única"), `src/goblinshift/platform/migration_locks.py`, `migrations/env.py`, `tests/migration_lock_check.py`, `tests/migration_sql.py`, `tests/test_migrations_lock_safety.py`, `tests/test_migration_lock_timeout.py`, `scripts/check_runtime_licenses.py`

## Contexto

O ADR 056 rodava todas as revisões pendentes numa transação só, com `statement_timeout` desligado. Um `ALTER TABLE` que pede ACCESS EXCLUSIVE numa tabela que outra sessão segura fica na fila do lock sem prazo, e toda consulta da API que chega depois espera atrás dele: o deploy congela o tráfego da tabela até a sessão concorrente terminar. Como a transação é única, o lock de cada migration já aplicada também fica preso até o fim do lote.

O engine da aplicação usa `statement_timeout=5000` e `lock_timeout=2000` (`platform/db.py`), valores pensados para requisições, curtos demais para um backfill ou um índice CONCURRENTLY.

Nada no CI barrava DDL que bloqueia leituras ou escritas por toda a duração: CREATE INDEX sem CONCURRENTLY, ADD CONSTRAINT sem NOT VALID, SET NOT NULL direto, ALTER COLUMN TYPE e ADD COLUMN com default volátil.

## Alternativas

| Alternativa | Prós | Contras |
|-------------|------|---------|
| **A. Transação única do ADR 056** | Falha desfaz o lote inteiro | Espera de lock sem prazo congela a API; locks das migrations anteriores ficam presos até o fim |
| **B. Só `lock_timeout`, sem retry** | Simples | Uma transação longa da API no momento do deploy derruba o deploy, embora o lock fosse sair em segundos |
| **C. Transação por migration, `lock_timeout` curto, retry com backoff e jitter, check estático no CI** (escolhida) | A espera atrás da migration fica limitada; uma disputa passageira não derruba o deploy; o padrão bloqueante é pego antes do merge | Um lote pode parar no meio, com parte das migrations aplicada; o check é estático e tem limites |
| **D. Ferramenta externa de migração online** (pg-osc, pgroll) | Reescreve sem lock longo | Dependência nova e operação mais complexa para um banco pequeno |

## Decisão

Opção C.

- **Tempos.** `MIGRATION_LOCK_TIMEOUT_MS = 5 000` e `MIGRATION_STATEMENT_TIMEOUT_MS = 15 min`, em `migration_locks.py`. A conexão das migrations aplica os dois com `SET` e faz commit antes de entregar a conexão ao Alembic, sobrepondo os valores do engine da aplicação. `-x lock_timeout_ms=<n>` troca o lock_timeout para testes; valor zero ou negativo é recusado com mensagem, porque 0 desliga o limite no PostgreSQL.
- **Transação por migration.** `transaction_per_migration=True` no modo online e no offline: cada migration confirma e solta os locks ao terminar. O script `--sql` começa com os mesmos `SET`.
- **Retry.** Só o erro 55P03 (`LockNotAvailable`) é repetido: até `LOCK_ATTEMPTS = 3` tentativas, com espera inicial de 1 s que dobra a cada vez, metade fixa e metade sorteada. A cada tentativa o Alembic relê a versão do banco, então nenhuma migration aplicada roda de novo. Statement timeout (57014) e qualquer outro erro não repetem: migration lenta não melhora ao repetir.
- **Desistência.** Esgotadas as tentativas, `CommandError` com "lock ocupado em N tentativas"; o processo sai com código diferente de zero, sem traceback. `api` e `worker` dependem do `migrate` com `service_completed_successfully`, então o deploy aborta antes da troca, e a versão anterior continua no ar sobre um schema que ela tolera (expand/contract, ADR 056).
- **Check no CI: negar por padrão.** `tests/test_migrations_lock_safety.py` analisa por AST o `upgrade()` das migrations a partir da 0019 e as funções do módulo que ele chama. Só passa sem `# lock-ok: <motivo>` (na linha da operação ou numa linha só de comentário logo acima) o que está numa allowlist curta, na forma segura de cada entrada; todo o resto pede a marca, inclusive o que o check não conhece. Assim um caso novo (como foi o `ALTER DOMAIN`) não passa calado: quem o conhece decide e escreve o motivo.
  - **Operações do Alembic** (`SAFE_OPERATIONS`, em `tests/migration_lock_check.py`): `create_table`; `create_index` e `drop_index` com `postgresql_concurrently=True`; `add_column` de coluna que não reescreve, não varre e não constrói índice (sem `unique`/`index`/`primary_key`, FK, CHECK, `Identity`, `Computed` persistida ou default volátil); `drop_column`; `alter_column` só com `nullable=True`, `server_default`, `comment` e os `existing_*`; `create_foreign_key` e `create_check_constraint` com `postgresql_not_valid=True`; `drop_constraint`; `bulk_insert`; `execute`/`exec_driver_sql` cujo SQL passe; e os auxiliares que não falam com o banco (`f`, `get_bind`, `get_context`, `inline_literal`). Conta como operação `op.x(...)`, com `op` ou um apelido dele, e o nome do `alembic.op` chamado solto (importado com ou sem apelido, ou por `import *`). `rename_table`, `drop_table`, `batch_alter_table`, `create_unique_constraint`, `create_primary_key` e qualquer operação nova pedem a marca.
  - **Instruções de SQL** (`SAFE_STATEMENTS` e `SAFE_ALTER_TABLE_COMMANDS`, em `tests/migration_sql.py`): DML (SELECT, INSERT, UPDATE, DELETE) e COMMENT; CREATE TABLE de tabela nova, sem `PARTITION OF` nem `INHERITS`, que travam a tabela-mãe; CREATE SCHEMA cujos elementos passem; CREATE INDEX, DROP INDEX, REINDEX e REFRESH MATERIALIZED VIEW com CONCURRENTLY; VACUUM e ANALYZE sem FULL; `ALTER TYPE ... ADD VALUE`; e ALTER TABLE em que todo subcomando é ADD COLUMN segura (sem `serial`, UNIQUE, PRIMARY KEY, FK, CHECK, IDENTITY, gerada STORED ou default volátil), DROP COLUMN, SET/DROP DEFAULT, DROP NOT NULL, ADD CONSTRAINT com NOT VALID (FK, CHECK, NOT NULL) ou `USING INDEX` (UNIQUE, PRIMARY KEY), VALIDATE CONSTRAINT, DROP CONSTRAINT, DETACH PARTITION CONCURRENTLY e FINALIZE. Fora dela, pedem a marca, por exemplo: SET NOT NULL, ALTER COLUMN TYPE, SET TABLESPACE, ATTACH PARTITION, LOCK, CLUSTER, VACUUM FULL, `ALTER DOMAIN`, CREATE TRIGGER, CREATE FUNCTION, GRANT, RENAME, DROP TABLE, `DO` (o corpo não é lido) e `SET` (um `SET lock_timeout = 0` desligaria a proteção).
  - **Cada entrada tem teste.** Um caso parametrizado por tipo de nó, por subcomando de ALTER TABLE e por operação da allowlist passa sem a marca, e um teste exige que os casos cubram exatamente as chaves das três allowlists: entrada nova sem caso reprova. Nós e operações desconhecidos pedem a marca.
  - O SQL é lido também quando montado em variável (inclusive com `+=`, na ordem do código, sem perder o valor de antes do acréscimo), f-string, concatenação, `format()`, `%` ou `.bindparams()`.
- **Leitura do SQL.** O texto montado vai para o pglast (dependência só de desenvolvimento, fixada), que embute o parser do próprio PostgreSQL (libpg_query): aspas, string de escape, dollar quoting, comentários, nomes com aspas e a dobra de caixa seguem as regras do servidor, sem regex. O texto é dividido em instruções pelo scanner do PostgreSQL e cada uma é parseada à parte; a que não parseia (valor desconhecido no lugar de uma palavra-chave, por exemplo) pede a marca, e CONCURRENTLY no meio dela continua exigindo o `autocommit_block` e a limpeza. Texto que nem o scanner aceita (aspas sem fechar) pede a marca e conta como concorrente. Tabela criada no mesmo `upgrade()` dispensa a marca, porque ninguém mais a enxerga.
- **CONCURRENTLY.** Só dentro de `op.get_context().autocommit_block()` e numa instrução por `execute`: várias instruções na mesma mensagem rodam numa transação implícita, que o PostgreSQL também recusa. Vale para índice (CREATE, DROP, REINDEX) e para DETACH PARTITION. O `lock_timeout` também vale para as esperas do CREATE INDEX CONCURRENTLY pelas transações antigas, e o timeout deixa um índice INVALID; por isso cada criação concorrente exige, antes e no mesmo bloco, `DROP INDEX CONCURRENTLY IF EXISTS` do mesmo índice, para o retry não falhar com "already exists". O nome é comparado como o PostgreSQL o guarda, parte a parte (schema e nome; sem aspas, só A–Z em minúsculas; com aspas, com a caixa e os espaços). O índice criado fica no schema da tabela do `ON`, então o DROP precisa do mesmo schema. Criação sem nome e nome que o check não resolve nunca contam como apagados.

## Consequências

- Um deploy pode parar com parte das migrations aplicada. Isso é seguro pelo expand/contract: a imagem anterior tolera o schema mais novo, e o próximo deploy continua da revisão em que o banco ficou.
- Durante a espera de uma migration, as consultas à tabela esperam até 5 s atrás dela, três vezes no pior caso. Isso é aceito em troca de um deploy que não congela.
- O check é estático: SQL vindo de arquivo, de parâmetro de função ou montado em laço, e chamadas indiretas (método de objeto, função de outro módulo) escapam dele. Ele peca pelo lado seguro nos casos ambíguos (pede a marca), inclusive quando o SQL tem mais de 16 montagens possíveis (atribuições alternativas, `+=`, concatenações): o resto não é lido e a operação pede a marca. SQL que o parser recusa por causa de um valor desconhecido também pede a marca, mesmo quando a instrução real seria segura, e o mesmo vale para coluna nova cujo tipo ou DEFAULT inteiro vem de um valor desconhecido.
- Negar por padrão gera falsos positivos aceitos: operação que não trava, mas está fora da allowlist (CREATE TRIGGER, GRANT, `drop_table`, índice comum dentro de um `CREATE SCHEMA` sobre a tabela que ele cria), pede a marca. O motivo escrito custa uma linha; ampliar a allowlist exige o caso de teste da entrada nova.
- O pglast é GPL-3.0-or-later e fica só no grupo `dev`: roda nos testes e no CI, nunca entra em imagem nem em pacote distribuído (os Dockerfiles instalam `--no-dev` ou só o grupo `executor`). A versão segue o PostgreSQL de produção: subir a major do servidor pede a versão do pglast com a libpg_query correspondente. A revisão do PR continua valendo.
- **Por que ele não pode sair do grupo `dev`.** Como ferramenta de CI, sem distribuição nem link com o produto, a GPL não alcança o código Apache-2.0. Numa dependência de runtime ou dentro de uma imagem publicada ele seria distribuído junto com a aplicação, e aí a GPL valeria para o conjunto. A precisão do parser do próprio PostgreSQL justifica a exceção; a alternativa permissiva (sqlparse) não segue as regras do servidor. `scripts/check_runtime_licenses.py` recusa o pglast pelo nome, qualquer pacote GPL ou AGPL, pela sigla ou pelo nome por extenso (LGPL passa), e pacote sem licença declarada. Roda nas dependências de runtime do lock, da aplicação e do executor (`tests/test_runtime_licenses.py`), e no build das duas imagens: um `RUN` com bind mount no estágio final de `docker/app.Dockerfile` e `docker/executor.Dockerfile`, que executa em cada plataforma (amd64 e arm64) e antes do push, então uma imagem recusada nunca chega ao registro. A imagem do executor também é conferida pronta (`tests/test_executor_image.py`, job do gVisor). Licença dupla com uma opção GPL (`MIT OR GPL-2.0-only`) é recusada; aceitá-la exige uma exceção pelo nome, registrada aqui. O check cobre pacotes Python; binários do sistema e o FFmpeg têm a licença decidida nos próprios ADRs (036).
- Uma função auxiliar do módulo que rode CONCURRENTLY fora do `autocommit_block` não é rastreada até o bloco de quem a chama; o PostgreSQL a recusa em runtime ("cannot run inside a transaction block"), então o erro aparece no primeiro teste de migration, não em produção.
- `alembic upgrade +N` recalcula o destino a cada tentativa. Em produção o único destino aceito é o head (ADR 056), então isso só afeta uso manual fora de produção.

## Compliance

- `tests/test_migration_locks.py`, sem banco: constantes, `SET` gerados, só 55P03 repete, esperas dobradas e sorteadas, mensagem ao esgotar, statement timeout sem repetição.
- `tests/test_migration_lock_timeout.py`, contra PostgreSQL real e pelo CLI, com uma sessão concorrente segurando a tabela em SHARE: a migration desiste em tempo limitado, com a versão inalterada e as leituras concorrentes esperando menos de 1,5 s; liberado o lock entre tentativas, a migration conclui; `lock_timeout_ms` 0 ou negativo é recusado com mensagem; o script offline traz o `SET lock_timeout` antes do primeiro DDL.
- `tests/test_runtime_licenses.py`: GPL, AGPL e pglast recusados, LGPL e permissivas aceitas, GPL por extenso e sem licença declarada recusados, ambiente vazio falha; as dependências de runtime do lock não têm nenhum deles; o estágio final dos dois Dockerfiles roda o check com a instrução exata, depois do último `COPY`.
- `tests/test_migrations_lock_safety.py`: as migrations existentes passam; cada padrão bloqueante sem a marca é recusado; cada entrada das allowlists tem um caso que passa sem a marca, e os casos cobrem exatamente as chaves delas; nós de SQL e operações fora delas pedem a marca, e com ela passam; a marca e as formas seguras passam; SQL que o parser recusa pede a marca; a análise de todas as migrations termina em menos de 2 s.
